Issue flow

One GitHub issue per feature is the only source of truth. Its pull requests follow it. Every request for a person is a comment on the issue that names the PR, so the issue page and its notifications are the one place to look. Click a status to see what happens, the labels on the issue and the PR, and what you have to do.

The top of the issue: what is happening, what to do

The issue's body starts with a status block for each of its PRs, which factory rewrites at every stage, phase, round, request and reply. Open the issue and the first lines tell you whether you must act. Your own text stays below it.

Several PRs on one issue

A PR contributes to exactly one issue, but an issue can have several PRs. The issue shows the earliest status among its open PRs, and blocked while any of them is blocked. It closes only when its last open PR merges. Set the PRs below and watch the issue.

What you reply

You always answer on the issue (replies on the PR work too). The request comment says exactly what to write.

Approve (plan or evidence)

/approve

The first line must be exactly /approve. Lines after it are kept as notes for the run:

/approve
Keep the reason field optional.

The approval holds for the requested commit only. A later push asks again. If change requests arrive together with /approve, the changes win.

Ask for changes

One change per line, naming the criterion. At the plan:

AC-7: an empty list says "Nothing to review" instead of showing an empty table.
Out of scope: exporting the list as CSV.

At the evidence:

AC-3 does not hold: after closing, the item is still in the list.
The button overlaps the title at phone width (the 390x844 screenshot).

Answer a question

For escalations such as a budget or round limit, a merge conflict, or anything the run can't decide. The question lists each option with its exact reply, for example:

continue
accept R3.P1

The whole comment goes to the run word for word.

Stop the run

Say so in the Claude Code session running it. factory closes the PR (state.sh end --stop), and the issue goes back to todo unless another PR works on it.

Other slash commands are ignored, and comments from people outside review.reviewers are listed but never acted on.

Finding what waits

gh issue list --label blocked          # waiting for you
gh issue list --label todo             # ready to be built: /factory2:run --issue <n>
gh issue list --label testing          # in review and QA (also planning, building, documenting)
gh pr list --label blocked             # the PRs those requests are about

Never set these labels by hand. scripts/issue-flow.sh recomputes them from the PRs, and factory's guard blocks changing them during a run. Outside factory, use the commands in skills/issue-flow: setup, start, status, block, unblock, merged, stop and show.

The PR's body

The issue is named at the top of every PR body. There is no Fixes or Closes keyword, so GitHub never closes the issue early:

<!-- issue-flow:issue=43 status=testing -->
Part of #43

The hidden marker records this PR's own status. The issue's labels are computed from the markers of all its open PRs.
